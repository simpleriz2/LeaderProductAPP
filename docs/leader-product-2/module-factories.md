# Remote factory contract and DB bootstrap ownership

Verified federation loaders can resolve ./Module only from the already verified complete active set, rechecking current pointer/session before and after loading. Metadata id/version/semantic contract/data schema must exactly match the signed artifact before the host passes ports. The factory creates a lifecycle instance; create must not start network/native/workers, init validates local capabilities, activate owns work, suspend aborts/awaits it, dispose releases it. Instances are recreated when needed. First supported Screen contract is a function component; other React wrapper representations require an explicit future contract revision.

Ports contain the captured confirmed account lease, one module's typed DB view, a Company service bound to ACTIVE release and module cancellation, and host operation-ID generation. No arbitrary endpoint setter/universal token/raw SQL/account-wide DB dispose. The factory cannot obtain another module's DB handle through its view. This enforces interface boundaries for trusted first-party modules; shared JavaScript is not a hostile-code sandbox.

The first QR migration history is compiled into the separate DB/bootstrap layer. Its source is modules/qr/schema.ts (no React/business runtime/network), explicitly owned by QR; draft/repository business code is delivered inside QR. The host registry may support only the exact histories it has compiled. New schemas require a tested DB-layer/host release and minHost gate until a separately verified staged migration-code loader exists. Ordinary QR JS/asset changes with the same schema can still update independently. A significant schema/contract change may update the release group/APK.

This conservative initial rule prevents executing a new business remote merely to make its own currently broken DB available. Bootstrap/recovery stays built-in. Unknown schema fails before activation; no guessed migration, arbitrary remote SQL or data downgrade. A future independent migration-code delivery path must prove cold bootstrap, signature/inventory checks before migration execution, no business side effects, interrupted preparation, and compatibility with last-known-good CURRENT data. Do not present exposing factory() as that completed migration executor.

Current acceptance: factory metadata/subject/lifecycle/data ownership validation unit tests plus target native-loader/Web compilation. Product module factory/Screen wiring, actual remote factory execution and native device behavior are still pending. See QR migration backlog; retained working feature has not been removed.

QR's static DB registry now retains base1->2 history: schema2 adds create-attempt receipts and preserves existing drafts. Its init/migration callbacks still contain no business runtime/network. A QR factory declaring schema2 cannot roll back to a schema1-only reader against current schema2 data; recovery must choose a compatible bundle/roll-forward. Original source data is retained, never silently selected as an older database.
